# Product Improvement Proposals — 2026-09-13

## User and market lens

The primary users are Swiss construction owners, contractors, and project teams who rely on BauCompliance while changing sessions, triaging Cases, and delegating compliance review. The highest-trust workflow moment today is account/session transition: after login, logout, or an auth-state change, the visible identity and every downstream owner-scoped query must belong to the latest session. A best-in-market compliance product must make tenant identity deterministic, keep primary Case work available when optional context fails, and make collaboration decisions audit-ready without weakening authorization.

## Small (S) — Keep Cases usable when optional protocol context fails

- **Target user and job-to-be-done:** An owner or project lead opening Cases to review defects and deadlines even when linked-protocol context is temporarily unavailable.
- **Problem:** The Case and protocol loads share one `Promise.all`; a protocol-query failure replaces successfully loaded Cases with a blocking retry state.
- **Scope:** Separate primary Case loading from optional protocol-count/context loading, retain Case cards on optional failure, and expose a truthful unavailable/retry state for protocol context.
- **Expected impact:** Fewer avoidable workflow outages and continued access to legally relevant Case data during a partial backend failure.
- **User-visible outcome:** Case cards remain usable while linked-protocol context reports that it could not load.
- **Competitive / best-product rationale:** A resilient compliance workspace should degrade additive context independently instead of hiding primary records.
- **Risk:** 3/10.
- **Effort/size:** Small; concentrated in `app/dashboard/cases/page.tsx` and focused Cases loading tests.
- **Phase-1 slice:** The proposal is already the smallest credible slice; no query/schema or protocol mutation changes.

## Medium (M) — Keep authenticated identity consistent across stale async completions

- **Target user and job-to-be-done:** An owner, contractor, or project teammate logging in, logging out, switching accounts, or returning to an existing session and expecting the dashboard to represent only the current identity.
- **Problem:** `AuthProvider` resolves profile names asynchronously. A slower lookup or initial `getSession()` completion can publish an older user after a newer auth event, logout, account switch, or unmount. Because dashboard data is owner-scoped, stale identity is a trust and tenant-separation risk, not merely a cosmetic name race.
- **Scope:** Stabilize the Supabase client for the provider lifetime; version auth events and profile lookups; ignore stale initial-session success/failure and stale profile completions after newer session state or unmount; invalidate pending profile work when logout begins; add provider-level controlled-promise regression tests.
- **Expected impact:** Prevents old account identity from resurfacing and protects downstream screens from reacting to stale auth context.
- **User-visible outcome:** The latest login/logout/account state remains authoritative even when earlier network requests finish later.
- **Competitive / best-product rationale:** Audit-oriented multi-tenant software must maintain deterministic identity boundaries under real network timing, especially before adding more collaboration writes.
- **Risk:** 4/10.
- **Effort/size:** Medium because the change crosses initial hydration, auth callbacks, login, logout, unmount lifecycle, and reusable test infrastructure even though production code is localized.
- **Phase-1 slice:** Guard client-side identity publication only. Do not change Supabase auth configuration, routing behavior, roles, tokens, profile schema, or data-query authorization.

## Large / strategic (L) — Append-only collaborator review decisions

- **Target user and job-to-be-done:** An authorized collaborator reviewing a shared compliance queue and returning a durable assessment to the owner.
- **Problem:** Shared queues are intentionally read-only, so review outcomes still leave BauCompliance through calls or messages and are not tied to the reviewed legal snapshot.
- **Scope:** Add two append-only review outcomes over a server-derived queue-row snapshot, with actor/owner/Case identity, timestamp, membership enforcement, immutable history, revocation semantics, and owner/collaborator visibility.
- **Expected impact:** Converts read-only sharing into an auditable collaboration loop while preserving owner authority over Cases and evidence.
- **User-visible outcome:** A collaborator can record a review decision and both parties can see immutable review history.
- **Competitive / best-product rationale:** Governed multi-party decisions are a strategic differentiator over generic task lists and document vaults.
- **Risk:** 8/10.
- **Effort/size:** Large; new RLS/mutation/privacy/retention contract plus UI and migration coverage.
- **Phase-1 slice:** Exactly two outcomes and immutable snapshots; no Case/checklist mutation, assignment, notification, comment, approval, or invitation workflow.
