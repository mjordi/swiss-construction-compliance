# Product Improvement Proposals — 2026-09-20

## User and market lens

**Primary user/job:** A Swiss construction owner, contractor, or project administrator managing account details and credentials must be certain that the Settings screen belongs only to the currently authenticated account.

**Workflow moment:** During logout, recovery, or rapid account replacement, profile and password requests from the previous session can remain in flight. The Settings page currently cancels only profile loading; older profile-save and password-update completions can still publish feedback or leave prior-account fields visible during the transition.

**Best-product outcome:** A best-in-market compliance product must make tenant boundaries obvious on every screen. When identity changes, account-specific fields disappear immediately, actions remain unavailable until the new profile is loaded, and stale asynchronous completions cannot affect the next account.

## Small (S) — Keep Cases usable when optional protocol context fails

- **Target user and job-to-be-done:** A Case owner who must continue defect, deadline, notice, checklist, and evidence work during a linked-protocol query outage.
- **Problem:** The Cases page currently treats primary Cases and optional protocol context as one success gate, so a protocol failure can hide valid Cases.
- **Scope:** Separate primary and protocol load states, show an accessible protocol-only warning/retry, represent protocol facts as unavailable rather than zero, and disable only exports that require complete protocol context.
- **Expected impact:** Preserves access to legally important Case work during partial service failures.
- **User-visible outcome:** Cases remain usable while linked-protocol counts and dependent exports are truthfully unavailable.
- **Competitive / best-product rationale:** A resilient compliance workspace should degrade by capability instead of blanking the primary legal record.
- **Risk:** 4/10.
- **Effort/size:** S.
- **Phase-1 slice:** The proposal is already bounded to read/load behavior; no schema or mutation changes.

## Medium (M) — Make Settings tenant-safe across account transitions

- **Target user and job-to-be-done:** An owner, contractor, or teammate signing out, completing password recovery, or switching accounts who must see and mutate only the current account's settings.
- **Problem:** Profile fields are not synchronously cleared when identity changes, and older profile-save/password-update completions and feedback timers are not scoped to the initiating account. A later account can briefly inherit stale fields, errors, success state, or pending state.
- **Scope:** Reset account-specific profile/password state immediately on identity change; keep profile actions disabled until the current account load settles; version load, save, and password requests against the current account and component lifetime; clear feedback timers; preserve newer edits and the existing recovery URL behavior.
- **Expected impact:** Closes a visible cross-account trust gap on an under-served product surface without changing auth, schema, routing, or password policy.
- **User-visible outcome:** Prior-account fields disappear immediately, the new account loads cleanly, and late completions from an old account cannot alter the current Settings screen.
- **Competitive / best-product rationale:** Strong tenant isolation must extend beyond backend authorization into every asynchronous UI transition, especially in a legal-compliance product.
- **Risk:** 4/10.
- **Effort/size:** M.
- **Phase-1 slice:** One Settings page plus controlled-promise regressions; no global state abstraction, auth-provider change, schema/RLS work, or new copy.

## Large / strategic (L) — Add append-only collaborator review decisions

- **Target user and job-to-be-done:** An invited contractor, adviser, or project teammate who needs to return an attributable conclusion without receiving owner mutation authority.
- **Problem:** The shared Work Queue is read-only, so collaboration remains one-way and has no immutable review-response history.
- **Scope:** Add two server-authored outcomes over a snapshotted queue item, active-membership write authority, and owner-visible immutable history.
- **Expected impact:** Closes the multi-party compliance review loop while preserving owner authority.
- **User-visible outcome:** Collaborators can record “reviewed” or “owner attention required,” and owners can audit actor, time, and reviewed context.
- **Competitive / best-product rationale:** Governed, attributable collaboration is a step-change beyond single-user tracking and generic comments.
- **Risk:** 8/10.
- **Effort/size:** L.
- **Phase-1 slice:** First establish an executable Supabase authorization/RLS integration gate and approve lifecycle semantics for snapshots, actor identity, revocation, retention/deletion, re-grant, and event cardinality; then ship the two outcomes without downstream Case mutations, assignments, comments, notifications, or approval semantics.
