# Product Improvement Proposals — 2026-09-23

## User and market lens

**Primary user/job:** A Swiss construction owner, contractor, project administrator, or authorized adviser needs one trustworthy action queue that surfaces both immediate defect-notice work and approaching acceptance-based warranty/limitation milestones.

**Workflow moment:** The shared Compliance Work Queue prioritizes notice urgency and readiness gaps, while the two-year warranty and five-year limitation milestones derived from a saved acceptance date remain isolated on the owner-only Deadlines page. A user or read-only collaborator can therefore open the product's action cockpit and miss a legally important milestone due within weeks.

**Best-product outcome:** A best-in-market Swiss construction-compliance product should make the next material legal milestone visible in the shared triage surface, reuse one tested deadline calculation, preserve owner/collaborator authorization boundaries, and avoid implying active monitoring or legal advice.

## Small (S) — Keep Cases usable when optional protocol context fails

- **Target user and job-to-be-done:** A Case owner who must continue defect, deadline, notice, checklist, and evidence work during a linked-protocol query outage.
- **Problem:** Cases and optional linked-protocol context are loaded through one success gate, so a protocol failure can hide valid Cases and block the primary legal workflow.
- **Scope:** Separate protocol readiness from primary Case loading, keep Cases usable, show an accessible protocol-only warning/retry, mark protocol facts unavailable rather than verified zero, and disable only exports that require verified protocol context.
- **Expected impact:** Preserves access to legally important Case work during partial service failures.
- **User-visible outcome:** Case cards and ordinary actions remain available while protocol-derived facts and dependent exports clearly show a degraded state.
- **Competitive / best-product rationale:** A resilient compliance workspace should degrade by capability instead of blanking the primary record.
- **Risk:** 4/10.
- **Effort/size:** S.
- **Phase-1 slice:** One page, localized warning copy, and focused async/retry/account-transition tests; no schema or mutation changes.

## Medium (M) — Bring imminent acceptance milestones into the shared Work Queue

- **Target user and job-to-be-done:** An owner or authorized read-only collaborator triaging the next compliance action across active projects.
- **Problem:** Saved acceptance dates already produce two-year warranty and five-year limitation milestones in the Deadlines portfolio, but the shared Work Queue snapshot omits the acceptance date and cannot surface milestones due soon. A fully ready Case can disappear from the action cockpit even when an acceptance-based deadline is within 30 days.
- **Scope:** Extend the narrow authorized queue snapshot with `acceptance_date`; reuse the existing deadline-portfolio calculation; include the nearest acceptance milestone due within 30 days; prioritize 0–14 days as urgent and 15–30 days as warning while keeping expired/immediate notice work first; render localized milestone type, fixed date, countdown, and next action for owner and shared read-only views.
- **Expected impact:** Turns the Work Queue into a more complete legal triage cockpit without duplicating deadline arithmetic or adding new mutation authority.
- **User-visible outcome:** An approaching two-year warranty or five-year limitation milestone appears where the user already decides what to do next, including in an authorized collaborator's read-only queue.
- **Competitive / best-product rationale:** The strongest products consolidate legally material action signals into one explainable, permission-aware queue instead of forcing users to reconcile separate screens.
- **Risk:** 5/10.
- **Effort/size:** M.
- **Phase-1 slice:** One additive migration that replaces the existing snapshot function, one domain adapter extension, one read-only UI extension, translations, and focused migration/domain/page tests. No notifications, assignments, acknowledgements, collaborator writes, calendar sync, or deadline-math changes.

## Large / strategic (L) — Add append-only collaborator review decisions

- **Target user and job-to-be-done:** An invited contractor, adviser, or project teammate who needs to return an attributable review conclusion without receiving owner mutation authority.
- **Problem:** The shared Work Queue is read-only, so collaboration remains one-way and has no immutable review-response history.
- **Scope:** Add two server-authored non-approval outcomes over a snapshotted queue item, active-membership write authority, and owner-visible immutable history.
- **Expected impact:** Closes the multi-party compliance review loop while preserving owner authority.
- **User-visible outcome:** Collaborators can record “reviewed” or “owner attention required,” and owners can audit actor, time, and reviewed context.
- **Competitive / best-product rationale:** Governed, attributable collaboration is a step-change beyond single-user tracking and generic comments.
- **Risk:** 8/10.
- **Effort/size:** L.
- **Phase-1 slice:** First add a reproducible local Supabase authorization test gate and approve a lifecycle ADR covering immutable snapshots, actor identity, revoke/write ordering, history visibility, retention/deletion, re-grant, and event cardinality. Only then implement the two outcomes without Case mutations, assignments, comments, notifications, or approval semantics.
