# Daily Product Improvement Proposals — 2026-09-12

## User and market lens

**Primary users / job-to-be-done:** Swiss construction owners, contractors, project administrators, and advisers need a finalized handover protocol they can inspect and hand off as faithful evidence of what was actually captured on site.

**Workflow moment:** Immediately after protocol finalization, or later when retrieving the finalized PDF from the Protocol Register or a Case dossier, the user must decide whether the portable artifact faithfully represents the stored record. The product persists the drawn signature image, but every generated PDF currently reduces it to the word `CAPTURED`; user-visible copy simultaneously claims cryptographic signing and legal validity that the implementation does not demonstrate.

**Best-product outcome:** A best-in-market construction-compliance product makes captured evidence visible in the exported artifact and describes its assurance boundary precisely. The artifact should carry the stored signature image wherever a finalized protocol PDF is generated, while the product must not imply qualified/electronic signature cryptography, legal binding effect, delivery, acceptance, or external retention that it cannot prove.

Repo signals:
- the finalized protocol builder already receives persisted `signature_data` for Protocol Register and Case dossier regeneration
- the fresh finalization flow has the SignaturePad data URI before saving, but drops it from the in-memory report used for download
- `AuditReportPDF` exposes only `CAPTURED` / `NOT CAPTURED`
- landing/success copy in all four locales and the README overstate cryptographic/legal guarantees
- the last run explicitly backlogged this trust gap because a copy-only patch would not improve the underlying artifact

## S — Show signature-image availability beside finalized records

- **Target user and job-to-be-done:** An owner or adviser scanning the Protocol Register before downloading evidence.
- **Problem:** The register says only whether a signature value exists; it does not disclose whether the captured image can be rendered safely into a regenerated PDF.
- **Scope:** Add a read-only localized `image available` / `image unavailable` indicator after detail load, without changing the PDF or persistence contract.
- **Expected impact:** Improves pre-download transparency but leaves the exported artifact unchanged.
- **User-visible outcome:** A user can see whether the record contains a renderable signature image before download.
- **Competitive / best-product rationale:** Evidence systems should disclose artifact completeness, but a register-only indicator is less valuable than fixing the artifact itself.
- **Risk:** 2/10.
- **Effort/size:** Small.

## M — Embed captured signatures in finalized protocol PDFs and correct trust claims

- **Target user and job-to-be-done:** A Swiss construction owner, contractor, project administrator, or adviser exporting a finalized protocol for close-out, audit, insurer/adviser review, or a dispute.
- **Problem:** The stored signature drawing is omitted from fresh and regenerated PDFs, while product copy claims cryptographic signing and legally binding evidence that is not implemented.
- **Scope:** Add a narrow typed signature-image contract that accepts only bounded PNG/JPEG base64 data URIs; carry the image through fresh and persisted finalized-report builders; render it in `AuditReportPDF`; degrade truthfully when historical data is absent or unsafe; replace unsupported cryptographic/legal-binding wording in DE/FR/IT/EN and README; add focused contract, PDF, flow-wiring, and locale-semantic tests.
- **Expected impact:** Makes the portable protocol more faithful to the finalized source record and removes a material legal-trust overclaim.
- **User-visible outcome:** Newly downloaded and regenerated finalized PDFs visibly include the captured signature when safely renderable, and product language accurately describes captured signatures and source-bound finalized records.
- **Competitive / best-product rationale:** Mature defect and handover tools preserve attributable evidence inside exportable reports. BauCompliance can differentiate through honest, source-bound evidence rather than unsupported signature certification claims.
- **Risk:** 4/10.
- **Effort/size:** Medium.
- **Phase-1 slice:** PNG/JPEG data-URI validation and PDF rendering only; no cryptographic signature, signer identity verification, countersignature, PDF persistence, schema/RLS change, delivery/acceptance semantics, or external retention.

## L — Add append-only collaborator review decisions

- **Target user and job-to-be-done:** An owner delegating compliance-queue review to a trusted collaborator who must record a conclusion with attribution.
- **Problem:** The governed shared queue is intentionally read-only; collaborator conclusions still leave BauCompliance and lose point-in-time provenance.
- **Scope:** Add tenant-isolated append-only review events with active-membership enforcement, actor and Case identity, two bounded outcomes, a server-derived queue snapshot, owner history, explicit revocation/read behavior, retention semantics, and RLS tests.
- **Expected impact:** Establishes the first auditable multi-party decision layer without granting collaborators Case mutation authority.
- **User-visible outcome:** Collaborators can record `reviewed` or `owner_attention_required`; owners can inspect who concluded what against which immutable queue snapshot.
- **Competitive / best-product rationale:** Attributable review queues are standard in mature defect systems and remain the largest strategic collaboration gap.
- **Risk:** 8/10.
- **Effort/size:** Large / strategic.
- **Phase-1 slice:** Two append-only outcomes over one server-snapshotted queue row; no Case/checklist/evidence/protocol mutation, assignments, notifications, approvals, delivery, or acceptance semantics.
