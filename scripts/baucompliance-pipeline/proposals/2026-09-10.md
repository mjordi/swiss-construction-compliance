# Daily Product Improvement Proposals — 2026-09-10

## User and market lens

**Primary users / job-to-be-done:** Swiss construction owners and project administrators need to start a legally traceable defect Case from the place where they expect project evidence to live, then collect deadlines, protocols, and evidence against that project.

**Workflow moment:** A first-time or returning user reaches the Vault and selects “New project” or the empty-state “Create project” action. Today both actions open the protocol wizard. A standalone protocol does not create the Case-backed project that powers the Vault, so the user can finish the apparent creation flow and still return to an empty Vault.

**Best-product outcome:** Best-in-market defect systems make each defect an actionable record with evidence, responsibility, deadlines, review state, and audit history. PlanRadar emphasizes evidence, assignee/deadline, reporting, approval queues, reminders, and escalation; Dalux separates ready-for-review from accepted/closed work. BauCompliance should make the foundational Case creation path unambiguous before adding deeper review transitions. Swiss deadline provenance also matters because the revised construction-defect rules effective 1 January 2026 introduced a 60-day notice period for hidden defects, making correct Case dates and source records operationally important.

## S — Align signature trust claims with the finalized record

- **Target user and job-to-be-done:** An owner, contractor, or adviser deciding whether a finalized protocol PDF is reliable evidence.
- **Problem:** The product persists a captured signature image but regenerated audit PDFs currently render only a “captured” status, while README/product wording includes stronger cryptographic/legal-signature claims that are not demonstrated by the implementation.
- **Scope:** Replace unsupported cryptographic/legal-binding wording on user-visible surfaces with precise captured-signature/finalized-record language; add locale-semantic tests. Do not change signing, PDF rendering, or persistence.
- **Expected impact:** Reduces legal-trust ambiguity and avoids overstating the evidence guarantee.
- **User-visible outcome:** Users see claims that match what the product can prove.
- **Competitive / best-product rationale:** Compliance software should state evidence guarantees precisely, but copy-only correction does not improve the underlying signature artifact.
- **Risk:** 2/10.
- **Effort/size:** Small.

## M — Make Vault project creation open a real Case workflow

- **Target user and job-to-be-done:** A construction owner or project administrator starting the first legally traceable project record from the Vault.
- **Problem:** All visible Vault “New/Create project” CTAs route to `/dashboard`, which creates a protocol rather than a Case. Because Vault projects are derived from Cases, the action can complete without creating anything that appears in the Vault.
- **Scope:** Route the shared Vault create-project helper to `/dashboard/cases?create=1`; consume and remove only `create=1` on the Cases page; preserve filters and unrelated query parameters; open the existing create form and focus its first required project-name field. Normalize invalid `create` values away without opening the form. Add focused helper, Vault CTA, and Cases URL-state tests.
- **Expected impact:** Repairs a broken activation loop and turns three existing CTAs into a direct path to the foundational Case record used by deadlines, evidence, protocols, and Vault views.
- **User-visible outcome:** Selecting “Create project” in the Vault immediately opens the Case form, ready for project details, and the URL is cleaned without losing the user’s existing view context.
- **Competitive / best-product rationale:** A best-in-market product should never send a project-creation intent into a different entity workflow. Correct entity creation is a prerequisite for the richer record, deadline, and review capabilities competitors expose.
- **Risk:** 3/10.
- **Effort/size:** Medium.
- **Phase-1 slice:** Reuse the existing Case form and URL normalization only; no schema, Case model, deadline calculation, protocol, Vault projection, persistence, or copy changes.

## L — Add append-only collaborator review decisions

- **Target user and job-to-be-done:** An owner delegating compliance-queue review to a trusted collaborator who must record a conclusion with attribution.
- **Problem:** The governed shared queue is intentionally read-only; collaborator conclusions still leave BauCompliance and lose point-in-time provenance.
- **Scope:** Add tenant-isolated append-only review events with active-membership enforcement, actor and Case identity, two bounded outcomes, server-derived queue snapshot, owner history, revocation behavior, retention semantics, and RLS coverage.
- **Expected impact:** Establishes the first auditable multi-party decision layer without granting collaborators Case mutation authority.
- **User-visible outcome:** Collaborators can record `reviewed` or `owner_attention_required`; owners see who concluded what against which immutable queue snapshot.
- **Competitive / best-product rationale:** Review/acceptance queues and attributable history are standard in mature defect systems; a Swiss-focused audit boundary can differentiate BauCompliance.
- **Risk:** 8/10.
- **Effort/size:** Large / strategic.
- **Phase-1 slice:** Two append-only outcomes over one server-snapshotted queue row; no Case/checklist/evidence/protocol mutation, assignments, notifications, approvals, or delivery semantics.
