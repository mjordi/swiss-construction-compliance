## APPROVED — Make Settings tenant-safe across account transitions

**User-impact note:** A Swiss construction owner, contractor, or teammate signing out, recovering access, or switching accounts must never see the previous account's name, company, password draft, errors, or stale success state. A real target user benefits at the identity-transition moment because prior state disappears immediately and only requests initiated for the current account can update the screen. This is not incremental polish: it extends tenant isolation into the asynchronous UI of the account-management surface that controls identity and credentials.

**Explicit engineering task:**

1. Reset profile fields, loaded snapshot, password draft, errors, success state, and pending state immediately when the authenticated account identity changes or disappears.
2. Keep profile controls unavailable until the current account's profile load settles successfully or with an error; never allow old visible values to be submitted for the new account.
3. Scope profile-load, profile-save, and password-update completions to the initiating account and current request generation; ignore older success, returned error, rejection, and `finally` paths after transition or unmount.
4. Track and clear profile/password success timers across new actions, account transitions, and unmount.
5. Preserve the existing newer-edit protection, stable Supabase client, recovery focus, and recovery-query cleanup behavior.
6. Add controlled-promise tests covering immediate old-profile/password clearing, stale load/save/password completion suppression, and current-account recovery.

**Guardrails:** Do not change Supabase auth configuration, tokens, schema/RLS, password policy, profile columns, routes, recovery query semantics, translation copy, or `AuthProvider`. Do not add a global store or cancellation dependency.

## Engineering outcome

Implemented on `pipeline/2026-09-20-daily-improvement`:

- account-bound profile fields, password drafts, errors, success feedback, and pending state are synchronously masked and then reset whenever the authenticated identity changes or disappears
- profile loads, profile saves, and password updates are scoped to the committed account and independent request generations, so older success, returned-error, rejection, and `finally` paths cannot affect the next account
- profile editing remains locked until the current account profile loads successfully, preventing an empty fallback from overwriting an unknown stored sibling field after a load failure
- tracked feedback timers are cleared on new edits, account transitions, and unmount; recovery focus/query cleanup and newer-edit preservation remain intact
- focused controlled-promise coverage includes account switch/logout, stale load/save/password outcomes, current-account operations, StrictMode replay, timers, and failure lockout

**Product review:** The implementation still delivers the approved user outcome. A target user changing identity on the Settings surface immediately loses access to prior-account values and cannot submit them for the next account. This is a visible tenant-trust improvement, not internal cleanup; it protects profile and credential workflows without changing auth, schema, routes, password policy, or recovery semantics.
