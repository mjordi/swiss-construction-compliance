## APPROVED — Keep authenticated identity consistent across stale async completions

**User-impact note:** A Swiss construction owner, contractor, or teammate at login, logout, account switching, or session restoration must see only the newest authenticated identity. A real target user benefits because a slow profile or initial-session response can no longer re-publish an older account after the session has changed. This is not incremental polish: auth context feeds every owner-scoped compliance screen, so deterministic identity publication protects tenant trust before broader collaborative writes are introduced.

**Explicit engineering task:**

1. Keep one stable Supabase client for the `AuthProvider` lifetime.
2. Version initial-session hydration and auth-state events so a late `getSession()` success or failure cannot overwrite a newer auth event.
3. Version asynchronous profile-name lookups so only the latest active session may publish the enriched user.
4. Invalidate pending profile work on logout and unmount without changing existing redirect behavior.
5. Add controlled-promise provider tests for account switch, logout, late initial session, unmount, and stable client identity.

**Guardrails:** Do not change Supabase auth configuration, tokens, schema, role/authorization policy, route destinations, login/signup API contracts, or profile fallback naming. Do not add global stores or cancellation dependencies.
