## Approved

### APPROVED — Establish the Case notice source-basis contract

**User-impact note:** The target user is a Swiss owner, contractor, project administrator, compliance lead, or adviser preparing a defect notice from an active case. The workflow moment is reviewing legally material source facts before drafting or delivery. A real user will notice because the Case will explicitly capture and review who should receive the notice, where it should be served, and which defect statement is the source allegation. This is not incremental polish: it removes the named blocker for the repeatedly deferred end-to-end notice workflow while preventing the product from fabricating legal facts.

**Explicit engineering task:** On branch `pipeline/2026-08-07-notice-source-basis`, add an additive migration and typed Case fields for nullable `notice_recipient_name`, `notice_recipient_address`, and `defect_statement`; extend existing create/edit forms to persist normalized values; show a localized read-only source-basis review block with complete/incomplete status and field values; preserve existing cases; and add focused migration/UI/locale tests. Do not generate/send notices, claim legal sufficiency, change deadline math, alter evidence/protocol/checklist behavior, or add delivery/reminder infrastructure.

## Backlogged

### BACKLOG — Generate, approve, deliver, and track a source-bound defect notice package

This remains the highest-value end-to-end outcome, but preview wording, human approval, immutable rendering, delivery channel, receipts, and legal claims are too risky for one daily PR. After today's source contract is proven, the smallest credible phase is a typed, explicitly non-sending preview that uses only the reviewed Case fields and existing dates/chronology.

## Rejected

### REJECTED — Show latest evidence provenance in the collapsed case snapshot

Safe and visible, but it would continue a heavily optimized evidence/Case surface without removing the strategic notice blocker. Its triage benefit is lower than establishing explicit source facts for the next core workflow.

## Engineering result

Implemented on `pipeline/2026-08-07-notice-source-basis`:

- Added nullable, bounded `notice_recipient_name`, `notice_recipient_address`, and `defect_statement` columns to the existing owner-protected Cases table without invalidating existing rows.
- Extended the established create and inline-edit flows with labeled, length-bounded recipient, service-address, and factual-defect fields; values are trimmed and whitespace-only inputs persist as `null` rather than ambiguous empty facts.
- Added a localized read-only source-basis review section to every Case card. It displays the persisted facts, explicitly identifies missing values, and only reports the basis complete when all three source facts exist.
- Added DE/FR/IT/EN copy plus focused migration-contract and UI coverage for complete/incomplete review, create normalization, edit hydration, and edit normalization.
- Kept notice generation, PDFs, sending, delivery receipts, reminders, deadline math, evidence, protocols, and checklist behavior out of scope.

## Product review after implementation

The shipped slice matches the approved user-impact note. A user preparing a defect notice can now record and review the intended recipient, service address, and factual defect statement directly on the Case, while incomplete existing cases visibly show what is missing. This removes a concrete prerequisite for a future source-bound notice preview and prevents the product from inferring legal facts. It does not claim that the data is legally sufficient and does not create or send a notice.
